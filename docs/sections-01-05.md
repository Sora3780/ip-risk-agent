# SECTION 01 · MVP 한 페이지 요약

## 1.1 한 문장 서비스 소개

> **소규모 개발팀을 위해, 작업 폴더와 Google Drive 를 계속 지켜보다가 파일이 바뀌는 순간
> 오픈소스 라이선스 충돌과 선행 특허 저촉 위험을 공공데이터 근거와 함께 알려주는 AI 에이전트.**

| 요약 항목 | 팀의 답변 |
|---|---|
| 해결할 문제 | 소규모 팀에는 IP 검토를 맡을 사람이 없다. 라이선스·특허 위험은 코드와 기획서에 들어간 뒤 투자 실사나 배포 직전에야 드러나고, 그때는 되돌리는 비용이 가장 크다. |
| 핵심 사용자/고객 | 5인 이하 스타트업·부트캠프 팀에서 개발과 문서를 겸하는 개발 리드. 법무 담당자가 없고 라이선스를 "MIT 겠거니" 하고 넘긴다. |
| 사용할 공공·산업 데이터 | ① 한국저작권위원회 오픈소스SW 라이선스정보 서비스_GW — 라이선스 84종 원문 조항 ② KIPRIS Plus — 특허 검색·서지·국문초록 3종 API ③ deps.dev — npm/PyPI 의존성 라이선스 해석 ④ PyPI JSON API — 해석 실패 시 보완 |
| Gemini 의 역할 | **판정이 아니라 설명.** 규칙 엔진이 정한 등급을 사용자 언어로 풀고, 배포 시 의무사항과 다음 조치를 뽑는다. 기획서 ↔ 특허 초록의 유사도 판단과 겹치는 문장 인용도 담당한다. |
| RAG 의 역할 | 84종 라이선스 원문(149 청크)에서 **이 사안에 해당하는 조항**을 찾아 인용한다. 설명의 출처를 만드는 것이 목적이며, 인용문이 원문에 실제로 있는지 문자열로 재검증한다. |
| MVP 핵심 기능 | 변경 감지(로컬 + Drive) → 규칙 판정 → RAG 근거 인용 → LLM 설명 → GUI 알림. 기획서가 바뀌면 KIPRIS 선행 특허 대조를 자동 수행. |
| 검증할 핵심 가설 | ① 규칙 엔진 + RAG 조합이 LLM 단독 판정보다 재현율과 근거 인용률이 높다. ② 3계층 증분 검사를 쓰면 상시 감시를 무료 등급 안에서 운영할 수 있다. |
| 성공 판단 기준 | 재현율 ≥ 90%, 정밀도 100%(오탐 0), 근거 인용률 ≥ 80%, 무변경 주기의 외부 API 호출 0건. **전부 충족(아래 실측).** |

## 1.2 프로젝트의 차별점

**① 판정은 규칙이 하고, 설명만 LLM 이 한다.**
SPDX 식별자 기반 규칙 엔진이 등급(위험/주의/확인)을 결정한다. 같은 입력에는 항상 같은 등급이 나오고,
왜 그 등급인지 코드로 추적된다. LLM 이 등급을 정하면 어제와 오늘의 답이 달라져 근거로 쓸 수 없다.

**② 근거를 인용하고, 그 인용을 검증한다.**
한국저작권위원회 원문 조항을 붙여 보여준다. 특허 대조에서는 LLM 이 인용한 문장이 원문에 문자열로
실제 존재하는지 대조해, 없으면 그 근거를 버린다. 지어낸 인용이 화면에 오르지 않게 하는 장치다.

**③ 상시 가동을 전제로 설계했다.**
의존성 캐시 · 판정 캐시 · 문서 해시의 3계층 증분 검사로, 바뀐 것만 다시 본다.
무변경 주기에는 외부 API 호출이 0건이라 감시를 켜 둔 채로 둘 수 있다.

# SECTION 02 · 문제 정의와 근거

## 2.1 문제 배경과 현황

오픈소스 없이 만드는 소프트웨어는 이제 없다. 문제는 오픈소스가 **공짜가 아니라 조건부**라는 점이다.
어떤 라이선스는 고지만 하면 되고, 어떤 라이선스는 우리 소스코드 전체의 공개를 요구한다.

소규모 팀에서 이 구분은 대개 확인되지 않는다. 법무 인력이 없고, 확인하려면 라이선스 원문을 읽어야 하며,
의존성은 매일 늘어난다. 그래서 검토는 "나중에 한 번" 으로 미뤄지고, 실제로는 투자 실사·오픈소스 고지 요구·
배포 직전에야 드러난다. 그 시점의 선택지는 **아키텍처를 갈아엎거나, 소스를 공개하거나, 재협상하거나** 셋뿐이다.

기획 문서 쪽은 더 확인되지 않는다. 아이디어가 이미 등록된 특허와 겹치는지 확인하려면 KIPRIS 를 직접
검색해야 하는데, 검색어를 어떻게 잡아야 하는지부터 알기 어렵다.

**지금 해결해야 하는 이유** — 위험은 파일이 저장되는 순간 들어온다. 검토 주기가 길수록 발견은 늦어지고
되돌릴 코드는 쌓인다. 검사를 사람이 시작하는 일이 아니라 **파일 변경에 딸린 자동 반응**으로 바꿔야 한다.

|---|---|---|---|---|
| **E1** | 공공데이터 | 한국저작권위원회 오픈소스SW 라이선스정보 서비스_GW (전 84종 수집·분류) | 84종 중 **41종(48.8%)** 이 단순 고지를 넘어 소스 공개·동일 라이선스 배포 등 추가 의무를 요구한다. (금지 11 · 제한 30 · 고지 42 · 검토 1) | 라이선스 종류의 절반이 "이름만 보고 넘길 수 없는" 것이다. 확인하지 않으면 절반의 경우에 의무를 모른 채 배포한다. |

## 2.2 핵심 문제 진술문

> **법무 인력이 없는 5인 이하 개발팀**은, 코드와 기획서를 매일 고치는 상황에서
> **어떤 의존성이 소스 공개 의무를 만들고 어떤 기획이 선행 특허와 겹치는지 확인하지 못한다.**
> 라이선스 원문을 읽을 시간과 지식이 없고, 검토를 사람이 시작해야 하기 때문이다.
> 이것이 해결되면 팀은 **위험이 들어온 그날 그 파일에서** 문제를 알게 되고,
> 배포 직전에 아키텍처를 갈아엎는 대신 의존성 하나를 교체하는 선택지를 갖는다.

## 2.3 문제 원인과 결과

| 층위 | 내용 |
|---|---|
| **표면 현상** | 배포·실사 직전에 "이거 GPL 인데요?" 가 나온다. 기획서를 다 쓰고 나서 유사 특허를 발견한다. |
| **근본 원인 ①** | 검토 시작점이 **사람** 이다. 아무도 시작하지 않으면 검토는 일어나지 않는다. |
| **근본 원인 ②** | 판단에 필요한 지식이 **라이선스 원문** 에 있다. 읽는 데 드는 시간이 확인을 막는다. |
| **근본 원인 ③** | 자동 조회 결과가 **불완전** 하다 (E3). 도구를 붙여도 최고 위험이 누락될 수 있다. |
| **결과** | 되돌리는 비용이 시간에 비례해 커진다. 첫날의 의존성 교체 = 10분, 배포 직전의 같은 문제 = 재설계. |
| **우리가 풀지 않는 것 (외부 요인)** | 법적 효력의 최종 판단, 특허 침해 여부의 법률 의견, 계약·협상. 이 도구는 **전문가에게 가져갈 근거를 만드는 것** 까지만 한다. |

## 3.2 조사·인터뷰에서 바뀐 가정

| 초기 가정 | 확인 결과 | 변경된 판단 |
|---|---|---|
| 공공 API 의 라이선스 판별 플래그(`optFinishLicenseYn`)를 그대로 쓰면 된다 | GPLv2 를 놓치고 ISC 를 오탐했다 | 플래그를 버리고 **SPDX 식별자 기반 규칙 엔진**을 직접 만들었다. 한국어 원문은 근거 인용에만 쓴다. |
| 라이선스 판정도 LLM 에게 맡기는 게 자연스럽다 | 같은 입력에 다른 등급이 나왔다 | **판정은 규칙, 설명은 LLM** 으로 역할을 갈랐다. 이것이 1.2 의 차별점 ① 이 되었다. |
| 특허도 RAG 로 처리하면 된다 | 특허는 전문(全文)을 사전 색인할 수 없고 신규 등록이 계속 늘어난다 | 특허는 RAG 가 아니라 **KIPRIS 실시간 검색 + LLM 판정** 경로로 분리했다 (SECTION 09.4). |
| 의존성 파일은 프로젝트 루트에 있다 | 실제 폴더에서 하위 디렉터리의 `requirements.txt` 를 통째로 놓쳤다 | 재귀 탐색(깊이 5)으로 바꿨다. 실제 폴더로 시험하지 않았으면 못 찾을 결함이었다. |
| 상시 감시는 비용 때문에 어렵다 | 3계층 증분 캐시로 무변경 주기 호출이 0건이 되었다 | **상시 가동을 기본값으로** 바꿨다 (UR-05 해소). |

# SECTION 04 · 솔루션과 가치 제안

## 4.1 제안 솔루션

```
[입력]  로컬 폴더 변경 (watchdog 파일 이벤트)
        Google Drive 폴더 변경 (modifiedTime 스냅샷 비교)
   │
   ▼
[1단계 · 규칙]      의존성 파일 파싱 → deps.dev/PyPI 로 SPDX 해석
   결정적            → SPDX 규칙 엔진이 등급 판정 (위험/주의/확인)
   API 호출 없음     → 소스 헤더·문서 표기 불일치 검사
   │
   ▼
[2단계 · RAG]       판정된 항목에만 실행
   84종 · 149청크    → 위험의 '원인' 라이선스로 필터 → 임베딩 유사도 검색
                     → 해당 조항 원문을 근거로 첨부
   │
   ▼
[3단계 · LLM]       Gemini 가 근거를 받아 설명·의무사항·조치 생성
   설명만 담당        → grounded=false 면 '참고용' 으로 낮춰 표기
   │
   ├── [문서 경로]   기획서가 바뀌면 → KIPRIS 검색 → 초록 대조
   │                 → 겹치는 문장을 양쪽에서 인용 → 원문 대조로 환각 검증
   ▼
[결과]  GUI 목록 (등급·위치·라이선스·유형) + 더블클릭 상세
        근거 원문 · 의무사항 · 다음 조치 · 특허 나란히 비교
   │
   ▼
[사용자의 다음 행동]  의존성 교체 · 라이선스 표기 수정 · 전문가 검토 의뢰
```

**AI 가 꼭 필요한 지점과 아닌 지점을 갈랐다.**

| 처리 | 담당 | 이유 |
|---|---|---|
| 의존성 목록 추출, 버전 파싱 | 일반 로직 | 규칙으로 완결된다. LLM 을 쓰면 느리고 비싸고 불안정하다. |
| SPDX → 등급 판정 | 일반 로직 (규칙 엔진) | **재현성이 근거의 조건이다.** 같은 입력에 같은 답이 나와야 한다. |
| 근거 조항 검색 | RAG (임베딩) | 84종 원문에서 사안에 맞는 조항을 찾는 일은 키워드로 안 된다. |
| 조항을 상황에 맞게 설명 | **Gemini** | 사용자의 프로젝트 맥락에 맞춰 풀어 쓰는 일은 규칙으로 못 한다. |
| 기획서 ↔ 특허 유사도 | **Gemini** | 표현이 달라도 같은 발명인지 판단하는 일. 문자열 비교로 불가능. |
| 인용문 진위 확인 | 일반 로직 (문자열 대조) | LLM 에게 자기 검증을 맡기지 않는다. |

## 4.3 대표 사용 시나리오

**시나리오 A — 라이선스 (주 흐름)**

1. 김도현이 앱을 켜고 프로젝트 폴더를 고른 뒤 **[감시 시작]** 을 누른다.
2. 최초 전체 검사가 돌고 진행률이 단계별로 표시된다. 결과 2건이 목록에 뜬다.
3. PDF 기능이 필요해 `requirements.txt` 에 `pymupdf` 를 추가하고 저장한다.
4. **몇 초 뒤 목록에 `위험 · requirements.txt:PyMuPDF · AGPL-3.0 · 라이선스 충돌` 이 노란 배경으로 추가된다.**
   이때 재검사된 것은 새 항목 1건뿐이고 기존 2건은 이전 결과를 재사용한다.
5. 더블클릭 → 한국저작권위원회 원문에서 **"소스코드를 제공"** 부분이 빨갛게 표시된 근거가 보인다.
   의무사항: *네트워크로 서비스만 제공해도 소스 공개 의무가 발생한다.*
6. 김도현은 `pypdf`(BSD) 로 교체한다. **소요 10분.** 배포 직전이었다면 기능 재작성이었다.

**시나리오 B — 특허 (문서 흐름)**

1. 팀 Drive 폴더를 감시 대상으로 지정한다. 기획서를 Google Docs 로 쓰고 있다.
2. 기획서에 "통화 음성으로 보이스피싱을 탐지" 절을 추가하고 저장한다.
3. Drive 변경이 감지되고, 문서 내용 해시가 바뀌었으므로 특허 대조가 자동 실행된다.
4. Gemini 가 검색어를 뽑아 KIPRIS 를 조회 → 후보 14건 → 상위 6건 판정 → **HIGH 2건**.
5. 목록에 `주의 · 기획서.md ~ 1020080080388 · 표절 위험` 이 뜬다.
6. 더블클릭하면 **검사 문서와 선행 특허 초록이 나란히** 놓이고, 겹치는 문장이 같은 색으로 칠해진다.
   "겹침: SMV 디코더에서 추출한 LPC 파라미터를 GMM 에 적용하는 구성" / "차이: 변별적 가중치 학습 부분은 없음"
7. 김도현은 이 화면을 캡처해 변리사에게 보낸다. **상담이 '뭘 봐 달라'가 아니라 '이 두 건'으로 시작된다.**
